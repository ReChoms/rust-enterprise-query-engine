Architecture Data Flow & Examples

This panel breaks down the exact data transformations happening at each critical stage of the RAG pipeline, mapping directly to the phases in the diagram.

Phase 1: Semantic Vector Retrieval

Step 1: execute_semantic_search
The user's intent is mathematically converted into a dense vector and compared against the LanceDB vector database. It returns a fast HashMap containing the closest semantic matches to allow O(1) instantaneous lookups during verification.

// Output: retrieved_chunks (HashMap)
{
  "doc_7781": "The Gamma Bakery account was created on 2023-11-04...",
  "doc_3390": "Gamma Bakery recently expanded operations into Austria..."
}

Step 2: build_semantic_prompt
The function stitches the HashMap values, the user's intent, and a strict JSON schema together into a single wall of text for the LLM to read.

// Output: Semantic Prompt (String)
You are an expert SAP data engineer...
CONTEXT:
CHUNK ID: doc_3390
TEXT: Gamma Bakery recently expanded operations into Austria...
RULES:
1. You must ONLY output raw JSON.
2. Match this schema...

Step 3: ask_llm
The application sends an HTTP request to the local LLM. The LLM responds with a raw, untrusted String. It might contain conversational markdown filler, and it might contain hallucinated quotes.

// Output: raw_llm_output (String)
```json
{
  "answer_found": true,
  "answer": "Gamma Bakery is located in Munich, Germany.",
  "exact_quote": "their headquarters and primary billing address remain in Munich",
  "source_chunk_id": "doc_3390"
}
```

Step 4: verify_and_parse_llm_generation (Anti-Hallucination Firewall)
We mathematically prove the AI has not hallucinated by forcing it to provide an exact quote, and then using Rust to physically verify that the quote exists verbatim in our database. We do not ask another AI to double-check the answer, nor do we allow fuzzy matching or paraphrasing.

// 1. Fetch real text using the AI's cited chunk ID
let source_text = retrieved_chunks.get("doc_3390");

// 2. Strict, byte-for-byte substring search
if !source_text.contains("their headquarters and primary billing...") {
    bail!("SECURITY VIOLATION: Hallucination detected.");
}

Because the .contains() method operates strictly at the binary level, it acts as an unbreakable deterministic firewall. It is physically impossible for the AI to trick the system by hallucinating extra commas, changing capitalization, or inventing facts. If the characters match perfectly, the data is mathematically proven to be grounded in reality. If the AI paraphrased even a single word, the function instantly throws an error and triggers Phase 2.

Phase 2: Literal Keyword Fallback

Step 5: execute_fallback_search
If Phase 1 fails (either because answer_found was false, or the AI hallucinated and failed the security check), the system abandons AI vector math entirely. It builds a strict, deterministic SQL query using the exact keywords from the user's intent.

// 1. Cleaned Intent String (Input)
intent = "Gamma Bakery"

// 2. Internal SQL Execution (Output)
"sentence LIKE '%Gamma%' AND sentence LIKE '%Bakery%'"

This catches obscure acronyms or exact part numbers that vector math is notoriously bad at finding. It returns a brand new HashMap of exact-match chunks.

Step 6: Re-run LLM Pipeline
The system passes this new HashMap right back into build_semantic_prompt, ask_llm, and verify_and_parse_llm_generation. Because the data structures are identical, the code is reused perfectly. The AI gets a second chance to read a completely different set of SAP documents.

Final Output

Once the validation passes (either in Phase 1 or Phase 2), the application yields a strictly-typed Rust object containing data mathematically guaranteed to be grounded in the database.

// Output: final_payload (SemanticResponse Struct)
SemanticResponse {
    answer_found: true,
    answer: "Gamma Bakery is located in Munich, Germany.",
    exact_quote: "their headquarters and primary billing address remain in Munich",
    source_chunk_id: "doc_3390",
}
